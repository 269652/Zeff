# Zeff launcher

An Electron app — Electron's own binary, not rebuilt: `Zeff.exe` on Windows, `Zeff.app` on macOS (renamed and signed ad hoc), `zeff-launcher` behind the `./zeff` start script on Linux. It runs Zeff's Next servers on the bundled Node and serves them over HTTPS:

| Address | Goes to |
| --- | --- |
| `https://zeff`, `https://zeff:1337` | Zeff, `127.0.0.1:9333` |
| `https://knowledge.zeff` | the knowledge server of the account you're in — one per account: `127.0.0.1:9555` (the first), `:9556` … (the others) |
| `http://zeff` | redirects to https |

- `lib/supervisor.js` runs `node next start [knowledge] -H 127.0.0.1 -p <port>` and restarts it after a crash (2 s … 60 s backoff). A port that's already held, for example by the old `Zeff Server` scheduled task, is shown as "not started by the launcher" and proxied as is. Servers a killed launcher left behind are cleaned up on the next start (`data/launcher/pids.json`).
- **Dev mode** (tray: "Dev mode (hot reload)", `--dev`, or `"dev": true` in the config) runs Zeff's server as `next dev` instead of `next start` — same port, so https://zeff, the proxy and its WebSocket tunnel (HMR) work unchanged, and edits show without `npm run deploy`. The tray toggle restarts Zeff's server and is kept in `data/launcher/dev-mode`. Needs `next.config.ts`' `allowedDevOrigins` (fed by `ZEFF_DEV_ORIGINS`, set by the launcher). It writes `.next/dev`, not the build a deploy swaps; the first page compiles slowly. The sync host and work host keep running their own code (last deploy / `work-host.mjs` as started), so changes to syncs and the scheduler still need a deploy. Production mode is a toggle away; the deploy script's busy checks don't know dev mode.
- **Nightly restart** (tray: "Restart Zeff nightly (04:30, when idle)", on by default; `"nightlyRestart": false` / `"nightlyRestartAt": "03:15"` in the config as the defaults; the tray switch is kept in `data/launcher/nightly-restart.json`) restarts Zeff's server once a night to give back the memory `next dev` grows to (4–6 GB): from the set time (local) as soon as no request has come through the https proxy for 10 minutes; still busy two hours later, that night is skipped. Only Zeff's server — the sync host, work host and knowledge servers keep running. The decision is `lib/nightly.js` (tests/launcher-nightly.test.ts).
- The **work host** (`scripts/work-host.mjs`, plain Node, `127.0.0.1:9334`, `workHost`/`workPort` in the config) starts Zeff's workers (Claude / Copilot CLI runs) — outside the Next server's process tree. A restart of Zeff's server (`npm run deploy`, a crash) leaves them running, so a work session can deploy Zeff without ending itself. The host tells Zeff when a worker ends (`POST /api/work/exit`, with a token the launcher keeps in `data/launcher/work-token`) and retries until Zeff is back. Without the host (no launcher, host down) the server starts workers itself, as before — then a session can't deploy (`npm run deploy` refuses). Live Copilot sessions (ACP) stay with the server.
- The **sync host** (`Sync`, `127.0.0.1:9336`, `syncHost`/`syncPort` in the config) is a second Zeff server from the same code (`ZEFF_ROLE=sync`, its own build folder `.next-sync`) that runs the syncs, the scheduler, the Ticket-Lage and the AI steps behind it, the day recap and the backups. Zeff's server (`ZEFF_ROLE=web`) hands those to it (`POST /api/sync-host`, a token the launcher keeps in `data/launcher/sync-token`), copies what it is doing (`src/lib/host/mirror.ts`) and gets told when something changed (`/api/host-event`) — so `npm run deploy` restarts the pages while a sync goes on. It only does so while `.next-sync/BUILD_ID` exists (the first `npm run deploy -- --sync` makes it; the launcher must have been restarted to know the service); without it Zeff's server does everything itself, as before. Release bundles don't ship `.next-sync` yet, so they run as before. See `docs/sync-host.md`.
- `lib/proxy.js` terminates TLS on 127.0.0.1 and routes by Host. It keeps the `Host` header and sets `X-Forwarded-Proto/Host/For`, so Next builds https URLs and Server Actions accept the origin. It rewrites `Location: http(s)://localhost:9333/…` back to the browser's address, because Next builds `request.url` from its bind address. Streams pass through and WebSocket upgrades are tunnelled.
- `lib/tls.js` makes the certificate — with Windows' own crypto (`ps/new-cert.ps1`), elsewhere with the system's `openssl`. A "Zeff Local CA" signs a certificate for `zeff`, `knowledge.zeff`, their `.localhost` twins, `localhost` and `127.0.0.1`, and then its private key is deleted. The server certificate lasts 825 days (macOS refuses longer ones) and is renewed a month before. The files are in `data/launcher/tls/`.
- `lib/setup.js` does the one part that needs admin rights: the hosts entry and trusting the CA. Windows: `ps/setup-elevated.ps1` behind UAC (hosts + the computer's Root store). macOS: `ps/setup-elevated.sh` through osascript's password dialog (hosts); the CA goes in the login keychain as the user. Linux: `ps/setup-elevated.sh` through pkexec (hosts + the system store); browsers read `~/.pki/nssdb`, which needs `certutil` (libnss3-tools). Declined, the CA is trusted per user where possible and Zeff is served on `https://127.0.0.1:1337`.
- `main.js` has the tray (open, start / stop / restart, logs, data folder, "Start at log in", setup, quit) and the status window (`status.html`). "Start at log in" (`lib/autostart.js`) is a per-user scheduled task on log on + unlock on Windows (Fast Startup skips log on), a LaunchAgent on macOS, an XDG autostart entry on Linux — where the launcher also puts itself in the applications menu.

The launcher finds Zeff in `app/` of the bundle (next to `Zeff.exe` and `./zeff`; in `Zeff.app/Contents/Resources/zeff`) or in the checkout it sits in. Options go in `zeff-launcher.json` (see `lib/config.js`) — next to the exe, in the data folder, or `--config <file>`. Data, state and logs are in `<data>`, `<data>/launcher` and `<data>/logs`: `<app>/data` in a checkout and the Windows bundle; `~/Library/Application Support/Zeff` and `~/.local/share/zeff` in the macOS and Linux bundles (Zeff.app may run read-only, and an update replaces the folder). The servers then get `DATABASE_PATH`, `ZEFF_CALENDAR_INBOX` and `KNOWLEDGE_DATA_DIR` pointing there, and `<data>/.env` is read for settings like `JIRA_URL`.

```
npm run launcher:start      # from the checkout (Node from PATH): npm --prefix launcher start
npm run dist -- --zip       # the bundle for this system in dist/Zeff (+ Zeff.zip / .tar.gz)
npm run launcher:build      # refresh only the launcher in an existing bundle
npm run release             # a release from HEAD: dist/release/Zeff-<version>-<os>-<arch>.zip|.tar.gz (+ .sha256), then the check below
npm run release:check -- <archive>   # unpack it, start it with --smoke-test on a bare PATH, run app/scripts/bundle-check.mjs
```

Flags: `--background` (tray only, no browser), `--no-setup` (no hosts/certificate prompt), `--config <file>`, `--smoke-test` (start everything on its own Electron profile, check Zeff and the knowledge server answer over https against Zeff's CA, quit; exit code 0 = ok).

**`npm run release`** (`scripts/dist.mjs --release [--ref <commit|tag>] [--no-check] [--allow-dirty] [--keep-build]`) builds a commit with `git archive` in `<temp>/zeff-release` (the checkout and `dist/` stay untouched), packs it, writes `<archive>.sha256`, prints the version (tag, else commit), size and sha256, and checks the archive it made. It refuses when uncommitted changes that belong in the build would be left out (`--allow-dirty`: build the commit as it is). **`npm run release:check -- <archive>`** (`scripts/smoke-release.mjs`) is the check: it unpacks into a fresh temp folder and starts the launcher with `--smoke-test` under a PATH holding only the system's folders (no Node, npm, git, uv, Chrome; `--inherit-env` keeps yours), on free ports and its own data folder — so a Zeff running on the machine is left alone. The servers start on the bundled Node, Zeff and the knowledge server answer over https against Zeff's CA, and the pages `/heute /todos /mail /kanban /plugins /sync-settings /auswerten /logins /feierabend /work /setup /jira /repos /documents` render. Then the bundled Node runs `app/scripts/bundle-check.mjs`: the files the app reads at run time are there, the production dependencies resolve, better-sqlite3 loads, each `src/plugins/<id>/driver.mjs` and the MCP scripts answer `initialize` + `tools/list`, `work-host.mjs` and `work-session-host.mjs` start and stop, the database is migrated to the last migration of `drizzle/meta/_journal.json`, and nothing of the build machine is inside (no data, `.env`, `zeff-launcher.json`, home folder, tokens). Exit code 0 only when all of it passed.

What the PC itself must bring (the automation browser, git, uv, the AI CLIs, Poppler) is in the main README ("Releases") and listed live on Zeff's Plugins and Setup pages (`src/lib/prerequisites.ts`). The launcher puts `runtime/` first on the servers' PATH, so the bundled `node` is the one worker sessions find; `npm`/`npx` are not in the bundle.

Releases for all three systems come from `.github/workflows/release.yml` (a tag `v*`): native modules (better-sqlite3) and the macOS bundle can only be built on their own system.
